## Nodemailer: why "breaking" and Google?

### Why npm calls it breaking

`npm audit fix --force` flags **any major-version jump** as breaking — nodemailer went 6 → 9 (skipping 7 and 8). That is semver caution, not proof our code breaks.

Our usage is minimal and unchanged across v9:

```typescript
nodemailer.createTransport({ host, port, secure, tls, auth? })
transporter.sendMail({ from, to, subject, html })
```

We do **not** use the vulnerable code paths from the advisories (`jsonTransport`, raw `envelope.size`, OAuth2 token fetch with loose TLS, etc.). The fixes in v9 harden address parsing and header handling — that's why we upgraded.

### Do you need new Google verification?

**No.** Nodemailer is only the SMTP **client library**. Production email goes through **Google Workspace SMTP relay** (`smtp-relay.gmail.com:587`, IP-whitelisted via NAT — see `terraform/variables.tf` and `docs/tech/architecture.md`).

Upgrading nodemailer does **not** change:

- SPF / DKIM DNS records (`terraform/email_dns.tf`)
- Google Admin → Apps → Google Workspace → Gmail → Routing → SMTP relay allowlist
- `EMAIL_HOST`, `EMAIL_FROM`, or relay authentication mode

No re-verification with Google is required for this dependency bump. After deploy, send one test invite or password-reset email to confirm relay still accepts traffic from the ECS NAT IP.

### Risk with no users yet

Immediate exploit risk is **low today** because:

- No public user registration volume yet
- Invite emails are generated by admins (not arbitrary internet users)
- Contact/consultation forms sanitize HTML before embedding in email bodies

It was still worth fixing **before first school customer**: org names and invite recipient addresses become attacker-controlled once managers bulk-invite from CSVs. The patched nodemailer closes CRLF/header-injection paths in those flows.
